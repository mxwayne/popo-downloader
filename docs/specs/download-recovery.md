# 下载恢复与失败项补下

目标：短暂目录异常不立即遗漏，用户能逐项补下失败文件或目录。

## 现状与证据

- 用户截图包含“遗漏 1 个目录”和“66 个完成、5 个未完成”。
- `processScanStep` 仅重试数量不一致；其他读取异常直接移出队列。
- 弹窗只提供整个任务的重试，失败预览最多保存 6 个文件。
- 已从用户登录的个人 Chrome 读取 Sentry 事件 `9739fa2f7e2942b2a608ad6e2949a3c1`：版本 0.7.9，`scanning / directory_loading`，`attempt=1`、`failureStage=目录加载失败`、`retrying=true`、`terminal=false`，24 成功、80 待处理。对应问题后续事件 `35e3cdcc8d3b40c0808bf748d3883806`：同一匿名任务与文件，`attempt=3`、`terminal=true`，24 成功、79 待处理、1 失败。两者指向父目录加载阶段；未携带具体异常，不能进一步断言网络或服务端根因。

## 需求与验收

- R1 / AC1：目录读取发生普通异常时最多自动重试 2 次，重建目录上下文；耗尽后记录失败并继续后续目录。数量核对保持严格。页面中断沿用工作区恢复预算。
- R2 / AC2：失败任务可展开全部失败明细，显示原目录、名称、失败阶段与原因；每项可手动单独重试。
- R3 / AC3：文件单项重试只扫描原父目录且只选择对应文件；目录单项重试只扫描该目录及子目录。保存目录不变，不重复交付其他文件。
- R4 / AC4：单项重试不丢失其他失败项及已有成功计数；重复点击不创建重复活动重试。对象消失仍保留失败，不能误报完成。目录内旧失败由新结果替换，目录外失败继续保留；取消补下后原失败仍可再次恢复。
- R5 / AC5：扫描重试、终止与手动恢复进入既有脱敏诊断；增加枚举错误分类、目录深度和遗漏目录数量，不上传原文件名、原路径、凭证或下载地址。
- R7 / AC7：文件准备阶段失败（Sentry 两个事件所在阶段）后不立即原地重试：第 1 次退避 3 秒，之后 10 秒；退避期内先处理其他待下载文件，任务不提前结束。
- R8 / AC8：扫描按虚拟列表行号去重。现场证据（2026-11-13，Dev 扩展本地状态）：`官方素材/劫妹/劫妹` 报“页面预计 77 项，实际稳定扫描到 78 项”，重扫 2 次结果相同；多出的一项是上一层目录残留的同名文件夹行。后读到的同号行覆盖先读到的行。
- R9 / AC9：进入子目录后地址改变的目录记为“有独立地址”。之后扫描该目录、定位其子目录、准备其文件时直接加载该地址，不再重载根目录逐层点击。地址或目录名在 3 秒内未确认、或加载出错时回退逐层进入。地址不变的目录保持逐层进入。
- R10 / AC10：英文与繁体界面下页面按钮正常挂载（锚点识别“All types”“所有類型”）。
- R6 / AC6：回归地址失效、Gopeed 断开/重启、后台重启、取消与多目录队列；运行 Windows 检查并同步固定 Dev 目录、核对身份。

## 范围与默认选择

使用现有 MV3、React、IndexedDB、Gopeed，不新增依赖。旧任务缺少可定位明细时保留整任务重试。失败明细置于弹窗，页面摘要保持现有职责。

比较：仅增加整任务重试不能满足逐项补下；替换下载引擎缺乏证据且扩大变更。本次补齐现有链路。

真实 POPO、Sentry 原事件、Windows 实际落盘均独立验收；不发布，不修改 Stable，不提交或推送。
