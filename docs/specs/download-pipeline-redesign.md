# 下载链路重设计：先扫后下、目录进度、页面快捷重试

状态：用户已确认（2026-11-16）；阶段一已实现，待 Windows 现场验收。接续 [download-recovery.md](download-recovery.md)（失败明细与单项补下已完成）。

## 目的

用户在层层嵌套、数量很大的素材空间里下载。现状有三个问题：

- 一次全下不稳定，逐个手动下太麻烦。
- 页面左下角面板只显示总数，失败项和重试入口只在扩展弹窗里。
- 小文件（如 77 张 png）看起来一个一个下，没有并发。

用户的选择（2026-11-16）：先扫完再下；失败后自动补一轮再交给人；面板按目录显示。

扩展弹窗负责设置与完整明细。页面面板负责日常快捷操作。

## 现状证据

- 并发只在 Gopeed 传输阶段。传输前的“准备”（加载父目录、点开文件、等预览、取下载地址）只有一个隐藏页面，串行执行。小文件传输比准备快，所以表现为逐个下载。
- `preparingItemId` 是单值，在 `background.js` 出现 26 次；隐藏页面由 `content.js` 创建，只有一个固定 ID。
- 当前扫描与交付交错：`choosePersistentWorkflowAction` 在有待下载文件时优先交付，扫描被穿插。
- 每个文件准备前都重新加载父目录（直达目录之后是一次页面加载，仍是最重的一步）。
- 现场 Dev 状态（2026-11-13）：每个目录的预计数、实际数已经记录，但没有按目录汇总给界面。

## 目标

- G1：扫描阶段结束时，用户看到“共 N 个目录、M 个文件”，每个目录有核对结果。
- G2：下载开始前，读取失败的目录已自动重扫。
- G3：页面面板按目录树显示进度；失败的目录和文件在面板里直接带“重试”。
- G4：准备步骤更快；连续失败时自动冷却，不耗尽剩余文件的重试次数。
- G5：失败的项目在整任务结束后自动补一轮，仍失败的才交给用户。

## 非目标与反目标

- 不替换 Gopeed、不改 Native Host、Agent、安装器，不新增依赖，不动 Stable，不提交。
- 不放宽目录数量核对。任何静默跳过目录的方案都算失败。
- 不做“按一级子文件夹分批”（用户未选）。

## 方案比较

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| 1（采用） | 在现有架构上加：扫描完成才交付、目录汇总、页面面板目录树、自动补一轮、同目录复用、冷却；同时加一个只读诊断，探明能否在扫描时拿到文件 ID | 改动集中，可分阶段验证；真正的并发要等诊断结果 |
| 2 | 现在就开多个隐藏页面并行准备 | 不依赖未知接口，但要改 26 处单值状态，并让 POPO 同时加载多页，与“更稳”相悖 |
| 3 | 重写成按目录批次的新流水线 | 最干净，但改动面最大，风险最高 |

采用方案 1。这是我的选择，不是用户逐项确认的。

## 设计

### 阶段一（现在构建）

1. **先扫后下（G1、G2）**：`processPersistentWorkflowStep` 在扫描队列与定位队列都清空之前，不选择交付。目录读取失败沿用现有自动重扫。扫描结束时写入目录汇总，然后自动开始下载。仍读取失败的目录不阻塞其他文件，列在面板里等重试。
2. **目录汇总（G1、G3）**：任务保存 `directories` 列表，每项含路径、预计数、实际数、成功数、失败数、状态（核对通过、读取失败、未核对）。由 `state.items` 与 `state.scanFailures` 计算，写入 `job`。目录数超过上限时，只保留有问题的目录和最近的目录。上限取 200，写在规格里，实现时可调。
3. **页面面板目录树（G3）**：`QueueDock` 的任务可展开，按目录显示“完成 a/b”“遗漏”“进行中”。失败项复用 `RETRY_JOB_ITEM`。把弹窗里的失败明细抽成共享组件 `FailureList`，弹窗与页面共用，避免两份实现。
4. **自动补一轮（G5）**：任务以失败结束，且有可重试项时，后台自动创建一次补下任务（同 `retryJob` 逻辑），标记 `autoRetryRound = 1`，最多一轮。`POPO_PERMISSION_DENIED` 与“文件已不存在”不自动补。
5. **同目录复用（G4）**：下一个待下载文件与当前隐藏页面在同一目录时，不重新加载目录。点开文件、取地址后，用页面历史返回目录，确认目录身份后继续。身份确认失败则回退到完整加载。预期节省的时间未实测。
6. **连续失败冷却（G4）**：连续 3 次准备失败后，暂停准备 30 秒再继续。冷却期间不消耗任何文件的重试次数。这是我加的，用来处理 POPO 短暂异常。
7. **只读诊断（为阶段二）**：扫描时记录目录行元素的属性名、页面请求目录列表接口的路径与返回字段名。不记录值、不记录文件名。结果出现在“诊断与回传”里，由用户在真实页面上触发一次。

### 阶段二（视诊断结果，另起规格）

- 若目录行或列表接口能给出文件 ID：下载时直接用 ID 调取址接口，不再打开预览，准备变成一次接口调用，可以真正并发（上限沿用 1 到 5 的并发设置）。
- 若拿不到文件 ID：阶段一的同目录复用与冷却就是本次的最终形态，不再继续优化准备并发。

## 验收

- AC1：扫描未结束时不创建 Gopeed 任务；扫描结束后自动开始。
- AC2：目录汇总的数量与 `state.items`、`scanFailures` 一致。
- AC3：页面面板展开后能看到失败目录和文件，点“重试”创建单项补下，与弹窗行为一致。
- AC4：任务失败结束后自动补一轮，且只补一轮；权限类失败不自动补。
- AC5：同目录文件不重载目录；目录身份确认失败时回退，不丢文件。
- AC6：连续 3 次准备失败触发冷却，冷却后文件重试次数不变。
- AC7：诊断只含属性名与字段名，不含文件名、路径、地址、凭证。
- AC8：现有测试全部通过；Windows 完整检查通过；同步 Dev 目录并核对身份。

## 留给实现者

- 目录汇总的存储位置（`job` 内嵌，还是单独的存储键）。要求：不使 `chrome.storage` 超限。
- 面板目录树的视觉细节：沿用现有深色卡片风格；窄面板下长路径折行。
- 真实 POPO 页面上的效果（同目录复用是否真的加速、诊断能否取到 ID）只能在用户的 Windows Dev 环境验证，验证记录标 NOT VERIFIED 直到现场确认。

## 实现与规格的差异

- 自动补一轮只针对原始任务；补下任务（自动或手动）失败后交给用户。
- `folder_not_found` 允许自动补；只有 `permission_denied` 与 `file_not_found` 不补。
- 目录进度组件名为 `DirectoryList`（扁平列表，问题目录在前），不是树。
- 同目录复用在“目录名与地址都对得上”时才生效，确认窗口 3 秒；其余回退完整加载。
